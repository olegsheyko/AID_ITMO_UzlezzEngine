# ЛР 1 — стабильность: загрузка на ходу, выход с живыми задачами, повторные запуски, длинная сессия

Снято 23.09.2026 на macOS, Apple M1 Pro, Release. Блок «Стабильность» ТЗ — четыре сценария, каждый проверен отдельно.

## Сценарий «стресс» для демо

В редакторе, панель Statistics → **Stress (lab 1) → Load and unload in a loop**: тяжёлая пачка
(12 текстур из `assets/models`) грузится через job system, держится 30 кадров и выгружается —
burst и stream по очереди. На экране — число циклов, ошибок, кадров длиннее 33 мс и память.
Тот же цикл из командной строки: `GameEngine --stress-seconds 900 --stress-out stress.txt`.

Утечку видно в начале цикла, когда прошлая пачка уже выгружена: там все циклы должны быть одинаковыми.
Два датчика — память процесса (`phys_footprint`, на Apple Silicon туда входят и GPU-текстуры)
и число живых текстур в OpenGL-адаптере.

## 1. Длинная сессия — 15 минут

`GameEngine --stress-seconds 900`

| Показатель | Результат |
|---|---:|
| Циклов загрузки и выгрузки | 1003 (~12 000 загрузок текстур) |
| Ошибок загрузки / из кэша | 0 / 0 |
| Кадров всего / длиннее 33 мс | 105 788 / 0 |
| Худший кадр | 25,0 мс |
| Живых GPU-текстур в начале цикла | 2 во всех 1003 циклах — это текстуры сцены |
| Память в начале цикла после прогрева | 772 МБ в среднем, ±30 МБ вокруг тренда |
| Тренд памяти, циклы 100–1000 | **+0,7 МБ на 100 циклов** — статистически ноль |

Первые ~150 циклов память растёт с ~180 до ~770 МБ и выходит на плато: это кэши системного `malloc`
(освобождённые крупные блоки он держит для повторного использования) и видеодрайвера. Для масштаба:
утечка одной текстуры 1024² за цикл дала бы +500 МБ на 100 циклов, 2048² — больше 2 ГБ.

## 2. Утечки памяти — `leaks`

`MallocStackLogging=1 leaks --atExit -- GameEngine --stress-seconds 20`

286 неосвобождённых блоков на 18 КБ — **все в системном фреймворке Apple** `AppIntents`:
XPC-соединение, которое он открывает при старте процесса, ссылается само на себя по кругу
(`ROOT CYCLE: <NSXPCConnection>`). Кадров движка в стеках выделения нет — **утечек в коде движка нет**.

## 3. Выход с живыми задачами

`GameEngine --bench burst --exit-during-load` выходит через кадр после запуска пачки, когда в полёте все 12 загрузок.

| Проверка | Результат |
|---|---:|
| Обычная сборка | 20 из 20 чистых выходов |
| ThreadSanitizer | 5 из 5, гонок 0 |

Порядок остановки: `ResourceManager::beginShutdown` (новые загрузки не принимаются, начатые сворачиваются)
→ `JobSystem::shutdown` (ждёт все задачи) → `clearCache` (разбор очереди заливки, удаление GPU-объектов).

## 4. Повторные запуски

`tools/stress_launches.sh 50` — 50 запусков подряд, каждый выходит в случайный момент цикла стресса,
каждый пятый — ровно посреди загрузки пачки.

**50 из 50 чистых выходов**: падений 0, зависаний 0, выходов без `Shutdown complete` 0.
20 выходов из 50 пришлись на живые загрузки — от 1 до 12 в полёте.

## 5. Гонки — ThreadSanitizer

Отдельная сборка `-fsanitize=thread`, весь движок:

| Прогон | Гонок |
|---|---:|
| `JobSystemTests`, 20 прогонов | 0 |
| burst и stream через job system | 0 |
| выход посреди загрузки, 5 прогонов | 0 |
| стресс 120 с, 29 циклов | 0 |

Что санитайзер действительно работает, проверено на заведомо гоночной программе: он сразу сообщает `data race`.

## Повторить

```bash
tools/stress_launches.sh 50
```

```bash
cd build/mac && ./GameEngine --stress-seconds 900 --stress-out bench/stress/soak.txt
```

На Windows: `GameEngine.exe --stress-seconds 300 --stress-out stress.txt` из папки с exe.
